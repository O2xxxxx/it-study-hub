MySQL 8 + InnoDB 索引排错清单（原创，可打印）
==============================================

一、先看执行计划
  EXPLAIN ANALYZE SELECT ... ;
  关注三列：type（ALL 最差）、rows（预估扫描行数）、Extra（Using filesort / Using temporary）。

二、六类常见索引失效
  1. 对索引列做函数或运算：WHERE DATE(created_at) = '2026-01-01'
     改为 WHERE created_at >= '2026-01-01 00:00:00' AND created_at < '2026-01-02'
  2. 隐式类型转换：user_id 是 BIGINT，却用 WHERE user_id = '12a'
  3. 前导通配：LIKE '%关键字'  无法走 B+ 树，改为全文索引或前缀索引
  4. 联合索引跳过最左列：(a,b,c) 只用 b、c 查询
  5. OR 连接不同列：WHERE a = 1 OR b = 2，除非两边都有索引否则走全表
  6. 区分度太低：status 只有 0/1 时，单独索引没意义，放进联合索引末尾

三、联合索引设计口诀
  等值在前，范围在后；排序字段跟着等值走。
  例：WHERE user_id = ? AND created_at > ? ORDER BY id DESC
  索引：(user_id, created_at) 已可用；若 ORDER BY 也要用索引，考虑 (user_id, id)。

四、回表与覆盖索引
  EXPLAIN 里 Extra = Using index 表示覆盖索引，不回表。
  把 SELECT * 换成需要的列，往往能让索引覆盖查询。

五、慢查询定位
  SET GLOBAL slow_query_log = ON;
  SET GLOBAL long_query_time = 1;
  日志在 datadir/*.slow.log，用 mysqldumpslow 汇总。

六、事务与锁
  - 唯一索引 → 行锁；无索引的 UPDATE → 可能锁全表。
  - 死锁查看：SHOW ENGINE INNODB STATUS，关注 LATEST DETECTED DEADLOCK。
  - 长事务会拖住 MVCC 的 undo 清理，监控 information_schema.innodb_trx。

七、建索引前问三个问题
  1. 这条 SQL 的 QPS 高吗？
  2. 过滤后剩余行数占总行数的比例小吗？
  3. 写入是否密集？索引越多写越慢。

八、上线前检查
  EXPLAIN 结果与线上真实数据量一致；用 SHOW INDEX FROM 表名 确认索引真的建成。
